Project Summary

In today’s day and age of mass marketing and having a broad consumer appeal, marketing campaigns have become bland, untargeted and deeply impersonal. Hyper-personalized campaigns have become a way of gaining an edge on competitors.  Email Intelligence RAG is an intelligence tool that turns large number of marketing emails, subject lines, HTML bodies and images into a searchable, explainable knowledgebase for marketers and analysts. Instead of shifting through large amounts of unstructured email campaigns, this tool allows for users to ask natural language queries and immediately explore results. This system aims to surface competitive signals, creative patterns and promotion trends from otherwise noisy, unstructured content allowing for faster and better-informed decisions.
	Email Intelligence RAG is a web system with a Python FastAPI backend and a lightweight React frontend. The email content is stored in a PostgreSQL database and, using SQL filters and semantic retrieval, users can directly query the database of emails to get natural language responses in a familiar chat-like UI. Answers are returned with citations to specific emails in the database.

Technical Details

Database Design:
The system will use a PostgreSQL as the main storage engine, extended with pgvector for similarity search. The schema stays lightweight. 
Emails Table:
-	Id (Primary key, Serial)
-	received_datetime (timestamp)
-	header_text (text)
-	sinppet_text (text)
-	body_html (text)
-	embedding (vector)

This design avoids derived tables, All the extracted insights are computed dynamically and returned in API response, not persisted. This keeps the database clean and avoids issues with stale precomputed fields.

Data Ingestion and Preprocessing:
The data in the header_text and the sinppet_text fields will be cleaned to make for clean inputs to create embeddings and the Hero image from the body HTML will be extracted by selecting the largest full width <img> tag. The Images will be fetched and analyzed to extract data. After the data ingestion the embeddings will be generated for header_text + sinppet_text and stored in the embedding column. 

Retrieval:
When the users send in the queries, the queries will be embedded and compared with the stored email embeddings. Cosine Similarity will be used in pgvector to determine the sematic similarity. Other filters like SQL conditions will be added to return the top-k candidate emails that are semantically and contextually relevant.

Backend (Python FastAPI):
FastAPI will provide endpoints to tie together the retrieval and augmentation. The embedding generation and the retrieval logic will be handled here. This will produce a structured JSON response for the frontend.

Frontend (React):
The React front end will focus on a chat style experience where the user will submit a query, and the backend will produce a structured JSON which will then be rendered as a conversational response. Each response will cite specific emails.

Tradeoffs:
1.	Using a hosted embedding is easier to set up but long-term costs and API dependencies are a risk. Open-Source alternatives can be considered later

Ethical Considerations

With AI and RAG transparency and bias can be issues. Considering that, the datastore used for this project is exclusively publicly available marketing materials and omits all personal identification information no recipient addresses, account data, names, or contact details are stored. During ingestion, obvious per-recipient tokens and residual identifiers are discarded. All the answers are grounded in evidence where the UI will cite specific emails (retailers, date, snippet) to support each claim. Minimal query logs are retained for debugging/evaluation only. To reduce model bias and hallucinations, the pipeline is “rules-first” (regex/heuristics for offers and dates), with the LLM used narrowly to normalize/validate text drawn from retrieved snippets. Periodic human spot-checks look for skew across brands, and removal requests will be honored.
